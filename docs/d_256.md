# FMHA 支持 head_dim D=256：问题与实验记录

针对 `fmha/fmha.py`（Blackwell SM100 tcgen05 融合 FMHA）。相关：[fmha.md](fmha.md)、TRT `kernelSrcs/build_cutedsl.py` / `fmha_cutedsl_blackwell/`。

---

## 1. 现象（已复现）

### 1.1 测试命令（示例）

```bash
python3 fmha/fmha.py \
  --qk_acc_dtype Float32 --pv_acc_dtype Float32 \
  --mma_tiler_mn 128,128 \
  --q_shape 1,968,8,256 --k_shape 1,968,8,256 \
  --is_persistent --warmup_iterations 10 --iterations 10 --skip_ref_check
```

（MHA：`H_q = H_k = 8`；`S_q = S_k = 968`；未加 `--is_causal`。）

### 1.2 结果

| D | launch | 说明 |
|---|--------|------|
| **128** | 正常 | 与上游/TRT `fmha_d128` 设计一致 |
| **192** | 失败 | `CUDA_ERROR_INVALID_VALUE` |
| **256** | 失败 | 同上 |

- **Compilation time ~3.8s** → JIT/编译成功。
- 失败点在 **`testing.benchmark` 首次 kernel launch**（`skip_ref_check` 时第一次跑 kernel 即在 benchmark）。
- 错误：`cutlass.base_dsl.common.DSLCudaRuntimeError: CUDA_ERROR_INVALID_VALUE (1)`。

### 1.3 已排除因素

- **序列长度 S=968**：D=128 同 S 可通过，非主因。
- **MHA vs GQA**：当前为 `H_q=H_k=8`（MHA）；GQA 应 `k_shape` 第三维为 `H_k`（如 8:1 → `q ...,8,...` / `k ...,1,...`），与 D 限制无关。

## 2. 根因分析

### 2.1 编译成功、运行失败说明什么？

属于 **kernel launch 参数不合法**（常见：**动态 SMEM 超限**），不是 Python 前端或 JIT 编译失败。

### 2.1 SMEM：每 CTA 随 D 线性增长（主因之一）

固定 pipeline（`BlackwellFusedMultiHeadAttentionForward._setup_attributes`）：

| 参数 | FP16 默认 |
|------|-----------|
| `q_stage` | 2 |
| `kv_stage` | 3 |
| `epi_stage` | 2 |

`SharedStorage` 中 sQ / sK（V 复用 K）/ sO 体积大致：

```text
sQ  ∝ q_stage  × M_tile × D
sK  ∝ kv_stage × N_tile × D
sO  ∝ epi_stage × 128 × D     # epi_tile = pv_mma_tiler[:2]
```

粗算（FP16，`M_tile=N_tile=128`，未含 swizzle/对齐/barrier）：

```text
合计 ≈ 128 × D × 14 字节

D=128  → ≈ 224 KB  （已在 Blackwell 每 CTA ~227KB 上限附近，故能跑）
D=192  → ≈ 336 KB  （超限 → INVALID_VALUE）
D=256  → ≈ 448 KB
```

Blackwell 动态 SMEM 上限约 **`(228-1)×1024` 字节**（与 `dense_gemm` SMEM 表一致）。

**结论**：D>128 时 SMEM 几乎必然超标；**D=192 即失败** 与「略大于 128 就顶满」一致。

### 2.2 TMEM：列布局按 D≤128 写死（主因之二）

`fmha.py` 中固定列偏移（为 **128×128** 分数块与 **O 宽 128 列** 设计）：

```text
tmem_s0_offset = 0
tmem_s1_offset = 128
tmem_p0_offset = 32
tmem_p1_offset = 160
tmem_o0_offset = 256
tmem_o1_offset = 384    # o0 与 o1 之间仅 128 列
```

- `alloc_tmem(get_max_tmem_alloc_cols("sm_100"))` → 最多 **512 列**。
- **D=128**：PV 的 `pv_mma_tiler = (128, 256, 128)` 中 O 的 N 维 = **D**；每块 O 占 **128 列** → 与 o0/o1 间距匹配。
- **D>128**：单块 O 需 **>128 列** → o0/o1 **重叠** 或总列数 >512。

**结论**：仅减 SMEM **不能** 解决 D>128；必须 **重排 TMEM map** 或 **D 方向分块（每块 ≤128）**。

### 2.3 上游/TRT 预期

- CUTLASS / `fmha.py` 文档：**head dim 32 / 64 / 128**。
- TRT `build_cutedsl.py` 仅预编译 **`fmha_d64` / `fmha_d128`**（及 SWA/FP8/ViT 变体）；`CuteDslFMHARunner::canImplement` 只接受 **64 或 128**。

## 3. 能否靠缩小 tile 等支持 D=256？

**可以，但是工程 trade-off**；不能只改 `q_shape` 最后一维。

### 3.1 手段对照

| 手段 | 降 SMEM？ | 解决 TMEM D>128？ | 工作量 | 性能风险 |
|------|-----------|-------------------|--------|----------|
| **减 stage**（q/kv/epi） | 是（同比） | 否 | 低 | 延迟隐藏变差 |
| **缩小 `mma_tiler_mn`（128→64）** | 是（MN 维） | 需重调 softmax/TMEM | 高 | tile 数增多 |
| **D 分块（2×128）** | 是（按 chunk 设计） | 可沿用 128 列布局 | 很高 | 相对可控 |
| **重排 TMEM offset** | 否 | 是 | 中～高 | — |
| **换 FMHA_v2 / 其它实现** | 视实现 | 视实现 | 集成 | 视产品 |

### 3.2 缩小序列 tile（128→64）

- SMEM 在 **M/N 方向** 约减半，但 **D 维仍整段进 SMEM**（`mma_tiler K = D`）。
- 文件要求 **`mma_tiler_mn = 128,128`**；softmax 等多处 **128 宽** 向量布局 → 改 64 需 **整条 warp 路径重调**，非单参数。
- D=256 + 64×64 tile：SMEM 粗算可与「D=128 + 128×128」同量级，**有可能** 压进上限，但仍要 **改 TMEM**。

### 3.3 减 stage（建议作第一步实验）

修改 `fmha/fmha.py` → `BlackwellFusedMultiHeadAttentionForward._setup_attributes`：

```python
self.q_stage = 1          # 原 2
self.kv_stage = 2         # 原 3（FP16）
self.epi_stage = 1        # 原 2
```

- 若 D=256 **仍** `INVALID_VALUE` → 优先查 **TMEM**。
- 若 D=256 **能 launch** → 再跑正确性 / 性能；再考虑是否够快。

### 3.4 D 方向分块（2×128，长期方案）

- 每次 SMEM 只承载 **D_chunk=128**；对同一 `(S_q, S_k)` tile 做 **2 段** QK + 与 online softmax 对齐的累加 / PV。
- SMEM 与现网 D=128 同量级；TMEM 可继续按 128 列规划。
- 需改 load/MMA/correction 主循环，**不是 CLI 参数**。

## 4. 推荐实验顺序（后续照此记录）

在文档下方 **§5 实验日志** 按行追加结果。

| 步骤 | 操作 | 目的 |
|------|------|------|
| **E0** | 基线：`D=128`，同 S/H | 确认环境 OK |
| **E1** | `D=144, 160, 176, 192` | 找 SMEM 临界 D |
| **E2** | `D=256` + 仅减 stage（§3.3） | 区分 SMEM vs TMEM |
| **E3** | E2 若仍失败：查 TMEM（改 offset 或 D-chunk 设计） | 解决 D>128 列布局 |
| **E4** | E2 若 launch 成功：去掉 `skip_ref_check` 做数值对比 | 正确性 |
| **E5** | 性能：`--benchmark` / NCU | 是否可接受 |

### 4.1 可选：Host 打印 SMEM 用量

在 `__call__` 建完 layout 后打印（便于对照 227KB）：

```python
print("cosize sQ bytes:", cute.size_in_bytes(self.q_dtype, q_smem_layout_staged))
print("cosize sK bytes:", cute.size_in_bytes(self.k_dtype, k_smem_layout_staged))
print("cosize sO bytes:", cute.size_in_bytes(self.c_dtype, o_smem_layout_staged))
```

### 4.2 GQA 参考（与 D 实验正交）

| 模式 | q_shape (B,S,H,D) | k_shape (B,S,H_k,D) |
|------|-------------------|---------------------|
| MHA | `1,968,8,D` | `1,968,8,D` |
| GQA 8:1 | `1,968,8,D` | `1,968,1,D` |

GQA 时 KV cache 为 `(B, 2, H_k, cap, D)`，内核用 `h_r=H_q//H_k` 广播 K/V，**不** 物理复制 8 份 KV。

## 6. 产品路径备忘

- **短期**：生产/Thor 继续 **D=64/128** + `build_cutedsl.py --kernels fmha --gpu_arch sm_110`。
- **若要 D=256 进 TRT**：在 Python 验证稳定后，增加 `fmha_d256` variant + `CuteDslFMHARunner` dispatch（与 d64/d128 同模式）。
- **若本 kernel 成本过高**：评估 **FMHA_v2** cubin 或其它 attention 后端。

---

## 7. 一句话结论

**D=128 正常、D≥192 失败** 说明当前 `fmha.py` 的 **SMEM stage 与 TMEM 列布局均按 D≤128 定死**；缩小序列 tile 或减 stage **可能** 缓解 SMEM，但 **D>128 必须改 TMEM 或做 D 分块**；不能仅靠增大 `q_shape`/`k_shape` 最后一维。
