# FMHA 支持 head_dim D=256：问题、根因与实验记录

针对 Blackwell SM100 **融合 FMHA**（tcgen05 + TMA + warp 专精）。同一套内核逻辑出现在：

| 位置 | 路径 |
|------|------|
| 学习/实验 | `study_cute/fmha/fmha.py` |
| TRT Edge-LLM（AOT / 产品） | `TensorRT-Edge-LLM/kernelSrcs/fmha_cutedsl_blackwell/fmha.py` |

相关：[fmha.md](fmha.md)、[support_d256.md](support_d256.md)（修改方案与 P0/P1 计划）、[dense_gemm.md](gemm/dense_gemm.md)、TRT `kernelSrcs/build_cutedsl.py`。

---

## 1. 现象（已复现）

### 1.1 测试命令

**study_cute：**

```bash
python3 fmha/fmha.py \
  --qk_acc_dtype Float32 --pv_acc_dtype Float32 \
  --mma_tiler_mn 128,128 \
  --q_shape 1,968,8,256 --k_shape 1,968,8,256 \
  --is_persistent --warmup_iterations 10 --iterations 10 --skip_ref_check
```

**Edge-LLM（路径替换为 `fmha_cutedsl_blackwell/fmha.py`，参数相同）：**

```bash
python3 kernelSrcs/fmha_cutedsl_blackwell/fmha.py \
  --qk_acc_dtype Float32 --pv_acc_dtype Float32 \
  --mma_tiler_mn 128,128 \
  --q_shape 1,968,8,256 --k_shape 1,968,8,256 \
  --is_persistent --warmup_iterations 10 --iterations 10 --skip_ref_check
```

（MHA：`H_q = H_k = 8`；`S_q = S_k = 968`；未加 `--is_causal`。）

### 1.2 结果

| D | launch | 说明 |
|---|--------|------|
| **≤128**（32/64/128） | 正常 | 与文档 / `fmha_d128` 设计一致 |
| **192** | 失败 | `CUDA_ERROR_INVALID_VALUE` |
| **256** | 失败 | 同上 |

- **Compilation ~3.8s** → JIT/AOT **编译成功**。
- 失败点在 **首次 kernel launch**（`skip_ref_check` 时多在 `testing.benchmark` 第一次跑 kernel）。
- 错误：`DSLCudaRuntimeError: CUDA_ERROR_INVALID_VALUE (1)`。

### 1.3 已排除因素

- **序列长度 S=968**：D=128 同 S 可通过。
- **MHA vs GQA**：与 D 限制正交；GQA 时 `k_shape` 第三维为 `H_k`（见 §4.2）。

### 1.4 官方 / 产品边界

- `fmha.py` 文件头：`* Supported head dimensions: 32, 64, and 128`；`* mma_tiler_mn must be 128,128`。
- `build_cutedsl.py` 仅 AOT **`fmha_d64` / `fmha_d128`**（及 SWA/FP8/ViT），**无 `fmha_d256`**。
- `CuteDslFMHARunner::canImplement`（`TensorRT-Edge-LLM/cpp/kernels/contextAttentionKernels/cuteDslFMHARunner.cpp`）：

```cpp
return (smVersion >= 100) && (headSize == 64 || headSize == 128);
```

ViT 路径额外支持 72/80，仍 **不含 256**。

## 2. 根因分析

### 2.1 编译成功、launch 失败说明什么？

属于 **kernel launch 参数不合法**（最常见：**动态 shared memory 超限**），不是 Python 前端或 DSL 编译失败。

### 2.2 D 如何进入 kernel：`mma_tiler` 与 `cta_tiler`

Host 侧将 `q_shape[-1]` 对齐到 MMA K atom（FP16 为 16）后写入 tiler：

```python
_MMA_K_ATOM = 256 // 16  # 16 for fp16
padded_d = ((d + _MMA_K_ATOM - 1) // _MMA_K_ATOM) * _MMA_K_ATOM
mma_tiler = (*mma_tiler_mn, padded_d)   # 默认 (128, 128, D)
```

类内（`BlackwellFusedMultiHeadAttentionForward.__init__`）：

```python
self.cta_tiler = (2 * mma_tiler[0], mma_tiler[1], mma_tiler[2])  # (256, 128, D)
self.qk_mma_tiler = mma_tiler                                      # (128, 128, D)
self.pv_mma_tiler = (mma_tiler[0], mma_tiler[2], mma_tiler[1])   # (128, D, 128)
```

`SharedStorage` 的 `sQ/sK/sO` 的 `cosize` 随 **D（mma_tiler[2]）** 增大；`head_dim` 仅影响 scale 与 TMA 边界，**SMEM 布局由 padded D 决定**。

### 2.3 SMEM：每 CTA 随 D 线性增长（主因之一）

固定 pipeline（`_setup_attributes`）：

| 参数 | FP16 默认 |
|------|-----------|
| `q_stage` | 2 |
| `kv_stage` | 3 |
| `epi_stage` | 2 |

`sQ / sK（V 复用 sK）/ sO` 体积大致：

```text
sQ  ∝ q_stage  × cta_M × D        # cta_M = 2×128 = 256
sK  ∝ kv_stage × N_tile × D       # N_tile = 128
sO  ∝ epi_stage × 128 × D         # epi_tile = pv_mma_tiler[:2] = (128, D)
```

粗算（FP16，未含 swizzle / 对齐 / barrier）：

```text
合计 ≈ D × (q_stage×256×2 + kv_stage×128×2 + epi_stage×128×2) 字节
     ≈ D × 14  KiB 量级（与 128×D×14 同阶）

D=128  → ≈ 224 KB  （贴近 Blackwell 每 CTA 动态 SMEM 上限 ~227KB，故能跑）
D=192  → ≈ 336 KB  （超限 → INVALID_VALUE）
D=256  → ≈ 448 KB
```

Blackwell 动态 SMEM 上限约 **`(228-1)×1024` 字节**（与 [dense_gemm.md](gemm/dense_gemm.md) 一致）。

**结论**：D>128 时 SMEM 几乎必然超标；**D=192 即失败** 与「D=128 已顶满」一致。

### 2.4 TMEM：列布局按 D≤128 写死（主因之二）

`fmha.py` 中 **编译期常量**（为 128×128 分数块与 **每 Q-tile 的 O 宽 128 列** 设计）：

```python
self.tmem_alloc_cols = cute.arch.get_max_tmem_alloc_cols("sm_100")  # 512 列
self.tmem_s0_offset = 0
self.tmem_s1_offset = 128
self.tmem_o0_offset = 256
self.tmem_o1_offset = 384    # 与 o0 间距仅 128 列
self.tmem_p0_offset = 32
self.tmem_p1_offset = 160
self.tmem_vec0_offset = 0
self.tmem_vec1_offset = 128
```

MMA warp 内对 O 的视图（`tOtO0` / `tOtO1` 对应双 Q tile）：

```python
tOtO0 = cute.make_tensor(tOtO.iterator + self.tmem_o0_offset, tOtO.layout)
tOtO1 = cute.make_tensor(tOtO.iterator + self.tmem_o1_offset, tOtO.layout)
```

- **QK** 的 S 为 **128×128**，与 D 无关。
- **PV** 的累加器形状 `partition_shape_C((128, D))`：**N 维 = D**。
- **D=128**：每块 O 占 **128 列** → `o0`/`o1` 间距 128 合理。
- **D>128**：每块 O 需 **>128 列** → 与 `o1_offset=384` **重叠**，或总占用超过 512 列。

**结论**：仅减 SMEM **不能** 单独解决 D>128；必须 **重排 TMEM map** 或 **D 方向分块（每块 ≤128）**。

### 2.5 算法与 warp 路径也按 128 宽假设（次要）

- `mma_tiler_mn` 必须为 **128,128**；softmax / correction 按 **128 宽** tile 组织。
- **不能** 只改 `q_shape`/`k_shape` 最后一维就支持 D=256。
- 每 CTA 已在 M 上承载 **2 个 Q tile**（`cta_tiler[0]=256`），SMEM 基线已偏高。

## 3. 手段对照：能否靠缩小 tile 等支持 D=256？

**可以，但是工程 trade-off**。

| 手段 | 降 SMEM？ | 解决 TMEM D>128？ | 工作量 | 性能风险 |
|------|-----------|-------------------|--------|----------|
| **减 stage**（q/kv/epi） | 是（同比） | 否 | 低 | 延迟隐藏变差 |
| **缩小 `mma_tiler_mn`（128→64）** | 是（MN 维） | 需重调 softmax/TMEM | 高 | tile 数增多 |
| **D 分块（2×128）** | 是（按 chunk） | 可沿用 128 列布局 | 很高 | 相对可控 |
| **重排 TMEM offset** | 否 | 是 | 中～高 | — |
| **FMHA_v2 / 其它后端** | 视实现 | 视实现 | 集成 | 视产品 |

### 3.1 缩小序列 tile（128→64）

- MN 减半可降 SMEM 的 M/N 部分，但 **D 仍整段进 SMEM**。
- softmax 等多处 **128 宽** → 改 64 需 **整条 warp 路径重调**。
- D=256 + 64×64 **有可能** 压 SMEM，但仍须 **改 TMEM**。

### 3.2 减 stage（建议第一步实验）

修改 `_setup_attributes`（`fmha.py` / `fmha_cutedsl_blackwell/fmha.py` 相同类名）：

```python
self.q_stage = 1          # 原 2
self.kv_stage = 2         # 原 3（FP16）
self.epi_stage = 1        # 原 2
```

| 结果 | 下一步 |
|------|--------|
| D=256 **仍** `INVALID_VALUE` | 优先 **TMEM / D 分块** |
| D=256 **能 launch** | 去 `skip_ref_check` 做数值对比，再 benchmark |

### 3.3 D 方向分块（2×128，CuTe 路径长期方案）

- 每次 SMEM 只承载 **D_chunk=128**；对同一 `(S_q, S_k)` tile 做 **2 段** QK + 与 **online softmax** 对齐的累加 / PV。
- SMEM 与现网 D=128 同量级；TMEM 可继续按 128 列规划。
- 需改 load / MMA / correction / epilogue 主循环，**不是 CLI 参数**。

### 3.4 重排 TMEM map（不做 D 分块时）

- 按 `D` 设置 `tmem_o1_offset = tmem_o0_offset + D`，并检查 P/vec 区不重叠，总和 ≤ 512 列。
- **仍须** 配合减 stage 或其它手段压 SMEM，否则 D=256 仍可能 launch 失败。

## 4. 支持 D=256 的推荐路径

| 路径 | 说明 | 适用 |
|------|------|------|
| **A. FMHA_v2 回退** | Edge-LLM plugin 在 CuTe 不支持时走 FMHA_v2；`fmha_v2` patch 含 **head_size=256** | **短期产品**：尽快跑通 D=256 |
| **B. 实验 E2（减 stage）** | 区分 SMEM vs TMEM 主因 | 开发验证 |
| **C. D 分块 2×128** | 与现网 D=128 资源模型一致 | **CuTe FMHA 本体长期方案** |
| **D. TMEM remap + 压 SMEM** | 不做分块时的折中 | 中工作量，D=256 仍紧 |
| **E. MN tile 64×64** | 整条 softmax/warp 重调 | 仅当 C/D 不够时考虑 |
| **F. `fmha_d256` AOT** | Python 稳定后：`build_cutedsl.py` + `CuteDslFMHARunner` dispatch | TRT 集成 |

## 5. 推荐实验顺序

在 **§8 实验日志** 按行追加结果。

| 步骤 | 操作 | 目的 |
|------|------|------|
| **E0** | 基线：`D=128`，同 S/H | 确认环境 OK |
| **E1** | `D=144, 160, 176, 192` | 找 SMEM 临界 D |
| **E2** | `D=256` + 仅减 stage（§3.2） | 区分 SMEM vs TMEM |
| **E3** | E2 仍失败 → TMEM offset 或 D-chunk 设计 | 解决 D>128 列布局 |
| **E4** | E2 launch 成功 → 去掉 `skip_ref_check` | 正确性 |
| **E5** | `--benchmark` / NCU | 性能 |

### 5.2 GQA 参考（与 D 实验正交）

| 模式 | q_shape (B,S,H,D) | k_shape / KV cache |
|------|-------------------|---------------------|
| MHA | `1,968,8,D` | `1,968,8,D` 或 cache `(B,2,H,D)` |
| GQA 8:1 | `1,968,8,D` | `1,968,1,D` 或 cache `(B,2,1,cap,D)` |

内核用 `h_r = H_q // H_k` 广播 K/V，**不** 物理复制多份 KV。

## 7. 产品路径备忘

- **短期**：生产 / Thor 继续 **D=64/128** + `build_cutedsl.py --kernels fmha --gpu_arch sm_110`。
- **要 D=256 且不改 CuTe kernel**：确认 **FMHA_v2** fallback 已启用。
- **要 D=256 走 CuTe**：完成 §5 实验 → **D 分块或 TMEM+SMEM 改造** → 增加 **`fmha_d256`** variant → 扩展 `canImplement` / runner dispatch。
- **成本过高**：维持 FMHA_v2 或其它 attention 后端。

## 9. 一句话结论

**D=128 正常、D≥192 失败**：当前 `fmha.py` 的 **SMEM stage 与 TMEM 列布局均按 D≤128 定死**；减 stage **可能** 缓解 SMEM，但 **D>128 必须改 TMEM 或做 D 分块**；不能仅靠增大 `q_shape`/`k_shape` 最后一维。产品侧 D=256 可并行 **FMHA_v2**；CuTe 路径优先 **D 分块 2×128**，再 **fmha_d256** AOT。
